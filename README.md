# عُدّة «من الفكرة إلى الأثر»

قالب عربي مفتوح المصدر لتخطيط مشروعات البحث والتعليم والخدمة المجتمعية وتنفيذها على دفعات صغيرة، مبني بوصفه **Preset لـ [GitHub Spec Kit](https://github.com/github/spec-kit)**. تصدره مبادرة مكتب خبرات طيبة للبحوث والدراسات، ويمكن لأي فريق استخدامه دون ارتباط بالمكتب أو بالمجلة.

**الحالة:** نموذج أولي `0.1.0` منشور في [مستودع مكتب خبرات طيبة](https://github.com/khibrattaibah/khibratgit)، قابل للتجربة المحلية؛ لم يُدرج بعد في فهرس Spec Kit ولم يُختبر تكامله مع جميع الوكلاء. لا يتضمن قاعدة بيانات أو خدمة مدفوعة أو مفتاح API.

**ملف تعريفي بالعربية والإنجليزية:** [تحميل PDF](docs/Research_to_Impact_AR_EN_Profile.pdf) (أربع صفحات A4).

## لماذا هذه العدة؟

تضيف إلى دورة Spec Kit أسئلة لا تظهر عادة في مشروع برمجي عام: ما المصدر الموثوق لكل معلومة؟ من يراجع المحتوى؟ ما حقوق إعادة استخدامه؟ كيف نثبت استخدام المنتج وما حد الاستنتاج من بياناته؟ ما أقل تجربة تكشف الحاجة قبل التوسع؟ لا تكرر محرك Spec Kit، بل تكيّف ثلاثة قوالب فيه: الدستور، والمواصفة، والخطة.

| المرحلة | الناتج | قرار المراجعة |
|---|---|---|
| دستور المشروع | قواعد الأدلة والحقوق والأمان ونطاق الصلاحية | يعتمد في أول commit قبل استقبال المساهمات |
| المواصفة | مشكلة، مستفيد، سيناريو مستقل، معيار قبول، سجل مصادر | هل الحاجة محددة وقابلة للاختبار؟ |
| الخطة | اختيار أدوات، وقت وتكلفة، مراجعة، قياس، رجوع | هل يمكن تنفيذ شريحة واحدة آمنة؟ |
| المهام والتنفيذ والتحقق | أدوات Spec Kit الأصلية | هل يطابق الناتج المواصفة ويجتاز قبولها؟ |

## التجربة خلال عشر دقائق

1. ثبّت [Spec Kit](https://github.com/github/spec-kit/blob/main/docs/installation.md) وفق دليله الرسمي، ثم نفّذ `specify version`. يتطلب Python 3.11+؛ يوصي الدليل باستعمال `uv`.
2. أنشئ مشروعًا تجريبيًا: `specify init tajriba --integration codex` أو اختر تكامل وكيلك المدعوم. انتقل إلى مجلد المشروع.
3. انسخ المستودع بالأمر `git clone https://github.com/khibrattaibah/khibratgit.git`، ثم نفّذ من داخل المشروع التجريبي: `specify preset add --dev /absolute/path/to/khibratgit` (استبدل المسار بمكانه الفعلي على جهازك).
4. تحقّق من القوالب: `specify preset resolve spec-template` ثم `specify preset resolve plan-template`. إذا كان الدستور قد تكوّن عند `init` فجدّده من قالب الدستور بعد مراجعة مبادئ مشروعك؛ تثبيت الـ Preset لا يعيد كتابة دستور موجود.
5. في وكيلك أنشئ الدستور أولًا، ثم مرّ بمراحل `specify → plan → tasks → implement → converge` كما يحدد [دليل Spec Kit](https://github.com/github/spec-kit/blob/main/docs/quickstart.md). في Codex تكون أسماء المهارات المحلية `$speckit-constitution` و`$speckit-specify` ونظائرها؛ تختلف الصيغة بحسب التكامل.

جرّب هذه الفكرة في مرحلة المواصفة: «أريد فهرسًا تجريبيًا لثلاث مواد منشورة، يُظهر العنوان والمصدر والمقتطف الصحيح ورابط النص الأصلي، ويتيح الإبلاغ عن خطأ في النص. لا تُعرض مادة قبل مراجعة حقوقها ودقة استخراجها». انظر [المثال المكتمل](examples/tadabbur-index/README.md).

**لمن يريد البدء بلا وكيل أو بلا تثبيت:** انسخ القوالب يدويًا إلى ثلاثة ملفات Markdown، املأ مواضع الأقواس المربعة، وسجّل المهام في GitHub Issues. البرمجة ليست شرطًا لصياغة المشكلة واختبارها.

## ما الذي يميّزه؟

- مسار مصدر ← تحويل ← مراجعة بشرية ← نشر ← تصحيح، مع حفظ حدود كل ادعاء.
- قبول قابل للقياس وتكلفة وقت/نقود ونقطة توقف؛ يصلح لفريق من مدير مشروع ومبرمج ومراجعين جزئيين.
- قوالب عامة للمؤسسات البحثية والتعليمية والمجتمعية، والمثال الأول من «فهرس تدبر» فقط؛ لا يربط جمهور العدة بمنتج تجاري.
- يعمل بملفات Git وMarkdown وبالأدوات الحالية؛ أي تكامل أو واجهة يحتاج مبررًا مستقلًا.

## النطاق والحقوق

العدة لا تضمن صحة المواد العلمية ولا تمنح ترخيصًا لأبحاث جهات أخرى. فحص الحقوق والمراجعة العلمية والموافقة على النشر تقع على مالك المشروع. استقلال القرار التحريري للمجلة محفوظ إذا استُخدمت موادها. لا تنسخ محتوى خاصًا أو بيانات شخصية إلى مستودع عام.

الشفرة والنصوص الأصلية في هذا المستودع برخصة [MIT](LICENSE). Spec Kit مشروع مستقل برخصته الخاصة؛ هذا المستودع لا يضم شفرته أو علامته، ولا يدّعي انتسابًا رسميًا إلى GitHub. المساهمة موضحة في [CONTRIBUTING.md](CONTRIBUTING.md)، والإبلاغ الأمني في [SECURITY.md](SECURITY.md).
